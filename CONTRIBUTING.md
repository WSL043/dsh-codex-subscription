# Contributing

Bug reports, focused fixes, compatibility updates, and small user-facing
improvements are welcome.

## Before changing code

- Use the issue forms for a reproducible bug or a concrete feature need.
- Keep one pull request focused on one problem. Do not bundle unrelated
  refactors, generated artifacts, or release preparation.
- Never include OAuth credentials, account identifiers, authorization links,
  proxy addresses, private machine paths, or raw account responses.
- Reuse DSH's native model, tool, attachment, settings, and plugin-lifecycle
  contracts instead of introducing a parallel subsystem.

## Local verification

Install the locked dependencies and run the complete repository check:

```sh
pnpm install --frozen-lockfile
pnpm run check
```

`lib/` is generated by the build and must not be edited by hand. If a change
affects the DSH UI or plugin lifecycle, also verify it in an actual supported
DSH installation; source tests alone are not installed-product acceptance.

Behavior tests are discovered automatically; new test files join that gate by
default. CI and release acceptance resolve the official `latest` and `alpha`
channels, test against their actual dependencies, and exercise the candidate
package lifecycle. Keep existing model capability assertions when allowing
legitimate additions to the upstream model catalog.

For a change that touches the DSH UI (slots, settings pages, the composer or the
model picker), also run the live UI smoke test on the target DSH version:
`node scripts/ui-smoke.mjs --dsh-version <version>`. It needs a signed-in
copy of the acceptance home and never calls the model; see
[docs/ui-smoke.md](docs/ui-smoke.md). When a new DSH version renames or adds
slots, refresh the slot snapshot described there.

Scheduled upstream checks do not publish automatically. Enable compatibility
publication only for a reviewed update that needs adaptation; an upstream
version change alone is not a reason to release.

## Pull requests

Describe the user-visible problem, the smallest implemented change, the checks
you ran, and any remaining compatibility or privacy risk. Keep README and
README.en.md behaviorally aligned when user instructions change. Public
documentation should explain the product and its supported use, not internal
debugging history or private design discussion.

Maintainers batch ordinary fixes into planned stable releases. A merged pull
request does not imply an immediate npm release.
Main may retain the current stable package version while unreleased fixes
accumulate; all runtime acceptance gates still apply. Version increments,
release tags and publication belong to the separately approved release.

## 参与维护 / Help maintain

希望长期参与问题复现、兼容性验证、文档或代码维护，可以提交[维护意向申请](https://github.com/WSL043/dsh-codex-subscription/issues/new?template=help-maintain.yml)，用中文或英文说明希望负责的方向、想先处理的具体问题，以及已有贡献。已有贡献链接和大致可投入时间可选，不需要公开私人联系方式。

可以先从一个聚焦的 Issue 或 PR 开始；普通贡献不需要先申请。项目负责人会结合实际贡献和验收记录沟通协作范围。申请不自动授予仓库写入、合并或发布权限，任何权限授予都需单独确认；main 合并和版本发布仍由项目负责人决定。

To help with ongoing issue reproduction, compatibility checks, documentation or code maintenance, submit the [maintenance interest form](https://github.com/WSL043/dsh-codex-subscription/issues/new?template=help-maintain.yml) in English or Chinese. Describe the area you would like to help with and a concrete first task. Previous contribution links and approximate availability are optional; do not include private contact details.

You can start with a focused issue or pull request; ordinary contributions do not require an application. The project owner will discuss a scope based on actual contributions and verification evidence. Applying does not automatically grant repository write access, merge rights or release permissions. Any access grant requires a separate decision; main merges and releases remain the project owner's decisions.
