# 官方 Codex 子代理出现后的取舍与接入方案

核对日期：2026-09-09；基于 DSH `dsh-v0.1.5-alpha.1`。这是后续方案，不表示已安装或接通官方子代理。本轮仍不发布 2.0。

## 判断

仅靠“在 DSH 用 Codex 订阅”确实不是持久优势。官方入口更容易获得信任和分发，换皮、堆型号和堆开关不足以扭转这一点。我们的现有订阅直连还依赖非公开订阅接口，其维护风险不应成为整个产品的基础。后续应优先复用官方执行能力，把可验证的价值放在用户完成任务的流程上；是否有人持续使用需要验证，不能用功能数量证明。

建议定位为 **DSH 的订阅与交付工作台**：用户选任务和资料、执行、检查产物、继续修改。保留订阅直连作为可选接入方式，不将自己维护 Codex 运行时作为竞争点。

## 能吸收什么

官方包是具名的 one-shot 子代理提供方，使用原生 Codex 身份与配置，每次新建临时进程和线程。当前只接受文本委派，主要返回最终文本；不提供多轮续接、过程流或图片输入，也不把子级用量返回父会话。这些限制来自 [官方 README](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.1.5-alpha.1/packages/subagent/subagent-codex/README.zh.md)。因此能复用它执行编码子任务，但不能直接替换现有主会话 Provider 或图片接口。

[提供方源码](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.1.5-alpha.1/packages/subagent/subagent-codex/src/index.ts)已在 `ctx.subagents` 注册执行器。[公共服务](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.1.5-alpha.1/packages/subagent/subagent/src/index.ts)提供 provider 查询与启动接口；我们不应复制它的 app-server 协议、进程管理或原生运行时。

| 范围 | 决策 | 理由 |
| --- | --- | --- |
| Codex 原生执行器、取消、进程回收 | 复用官方可选包 | 减少重复适配；版本随官方包维护 |
| 后台任务状态、结果、取消 | 复用 DSH Jobs / 子代理工具 | 不自建第二套任务调度器 |
| 子代理登录、模型与权限 | 保留官方配置权威 | 不复制插件 OAuth 到原生 Codex，也不把两份账号状态混在一起 |
| 多轮订阅对话、额度、搜索 | 暂时保留现有接入 | 官方 one-shot 子代理尚不能替代；未来同等能力成熟后再迁移 |
| 绘图、原图引用、比较与修改流程 | 保留并简化 | 与当前官方子代理的用途不同，但仍需要用户验证价值 |
| 通用文件查看、Sidebar、原生控件 | 优先复用 DSH | 不维护平行的应用外壳；可用性不足时才保留局部适配 |
| “所有工具都做一遍”的插件集合 | 不做 | 增加兼容负担，不能形成明确使用理由 |

## 最小接入方案

1. **只读发现。** 可选注入 `subagents`，使用公共 provider 查询和增删通知判断已注册的提供方。不能将注册成功显示为已登录或可执行；需要一次明确的实际任务验证。允许部署自定义 provider 名称，不硬编码认为一定叫 `codex`。
2. **明确委派。** 首版只复用已有 `dsh-tool-subagent` 与 Jobs 链路。界面显示“交给 Codex 子任务”，用户确认任务文本和工作区再执行；仅安装可选包不自动启用所有 agent 的工具。
3. **限定上下文。** 提交用户选定的需求与必要文本，不搬运整个聊天。当前提供方不支持图片块，不把图像悄悄丢弃后继续；相关任务留在支持图片的订阅会话中。文本裁剪必须明示，不静默截掉关键验收条件。
4. **沿用生命周期。** 如后续确需自有按钮，薄适配器通过 `subagents.start` 传入当前显式 Agent、文本与取消信号，并负责收尾；不启动自有 CLI 进程。没有当前 Agent 或有效工作区就不提交。任务结果回到原会话的官方工具结果与 Jobs 状态。
5. **身份和用量不伪统一。** 官方子任务可能使用与本插件不同的账号或原生配置。不能把插件额度当成它的可用额度，也不能宣称安装即完成登录。其结果不含精确用量时，界面不编造成本。
6. **失败可判断。** 区分缺失提供方、未通过原生登录/权限、取消、执行失败和结果缺失；有副作用的任务不自动重试，不自动切换到另一个收费后端。移除可选包不破坏原有订阅对话。

首个可验收切片：在隔离工作区提交一个文本编码任务 → 使用官方执行器 → 通过官方任务状态观察完成 → 打开实际产物核验 → 测试取消与未登录失败。完成前不在 README 宣称“官方原生集成已支持”。

## 值得验证的突破方向

优先级不是模型数量，而是三个可比较的用户结果：

1. **从任务到可检查的交付物。** 预先填写验收条件，结束后展示产物入口、已有 Git 仓库的变更和检查结果。基线必须在提交前记录；工作区差异需要从工作区单独核验，不能伪装成官方子代理返回的数据。先做“一次任务 → 一个可检查结果”，不自建项目管理系统。
2. **连续图片修改。** 明确选源图、写修改要求、对比、导出，不必让用户记附件编号。先把当前功能做稳定；没有可靠父图关系就不做虚假的版本树。若 DSH 原生查看器覆盖同等流程，删除重复实现。
3. **低配置成本。** 从原生插件管理器进入安装和配置流程，清楚说明两种账号来源及适合的任务；只有三个图片功能分组，默认状态可用。把异常恢复和升级兼容做实，不用更多开关弥补设计问题。

## 验证与停止条件

- 先请 5 位目标用户做同一组任务，对比纯 DSH + 官方子代理与本插件：首次完成时间、需要解释的步骤、失败恢复是否成功、一周后是否再次使用。小样本只用于发现问题，不当市场份额证明。
- 分发内容围绕真实案例和可复现的产物，不围绕“支持更多型号”的名单。争取成为官方生态里的可选工作流，而不是依靠与官方抢入口流量。
- 如果用户不愿重复使用额外流程，停止扩大产品范围；维护成轻量兼容插件即可。如果官方已覆盖某个功能且体验不差，优先迁移、删除重复代码。
- 不承诺流量、收入或竞争壁垒。只有真实复用、成功交付及更低操作负担，才说明这个方向值得继续投入。

## 顺序

**当前 2.0：** 修复深浅主题和菜单交互、简化设置、用户实机验收。**下一个小版本：** 官方子代理发现与一个完整委派流程，先在隔离环境验证。**之后：** 根据用户重复使用数据决定交付物面板或图片修改流程的投入，不提前把两条线一起扩成大平台。
