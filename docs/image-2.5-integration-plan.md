# Image 2.5 差异与订阅插件接入方案

研究日期：2026-09-09。本文保留最初的能力分析与阶段方案；实际候选版已调整为 **2.0.0，尚未发布**。已实现范围和证据以 [2.0 架构](2.0.0-architecture.md) 与 [验收记录](2.0.0-acceptance.md) 为准。Flare 已完成一次真实订阅生图；服务端未报告实际型号，Sunburst 尚未实测，不能把下面的规划全部视为已交付。

## 已确认的产品差异

| 模型 | 官方定位 | 插件中的建议用途 |
| --- | --- | --- |
| GPT Image 2 | 现有生图和编辑模型 | 保留当前已实测路线与历史图片编辑兼容 |
| GPT Image 2.5 Flare | 偏速度的日常高质量生图，也接受图片输入 | 订阅验证通过后作为日常生成、快速修改的优先选项 |
| GPT Image 2.5 Sunburst | 更重视编辑精度 | 用户明确选择的精细编辑选项，不自动将所有编辑切过去 |

两款 2.5 的公开 API 均支持 `auto/low/medium/high/xhigh/max`，新增的高质量档位是 `xhigh/max`。官方角色区分见 [Flare 模型页](https://developers.openai.com/api/docs/models/gpt-image-2.5-flare) 和 [Sunburst 模型页](https://developers.openai.com/api/docs/models/gpt-image-2.5-sunburst)。推荐用途属于本项目的实现建议，不是对订阅用量或实际速度的保证。

[API 生图指南](https://developers.openai.com/api/docs/guides/image-generation)还描述了多轮编辑、蒙版、部分图流式返回、输出格式等能力。这些不能统称为 2.5 新增能力，更不能直接复制为 Codex 订阅请求字段。指南区分主对话模型与图片工具模型：Luna 可以负责调用工具，实际出图模型另选；选择 Luna 不等于图片部分也按 Luna 的用量计算。

## 现有插件的实际差距

代码核对基线：`38d249f`。

- `src/codex-images.js` 固定 `IMAGE_MODEL = gpt-image-2`，工具没有图片模型选择参数。
- 质量校验和工具枚举均只接受 `auto/low/medium/high`。即使服务端开放新档位，当前插件也会先拒绝。
- 订阅请求使用 `chatgpt.com/backend-api/codex/images/generations` 与 `/edits`，OAuth 和账号头由现有主机服务提供；这不是公共 API 的 `/v1/images/*`。
- 返回处理、原图存储和工具结果只处理 PNG，不能只加 JPEG/WebP 选项就宣称支持这些格式。
- 返回元数据保留质量、尺寸等，但没有区分“请求模型”和“服务端报告模型”。成功得到图片并不足以证明具体后端型号。
- 昨日请求 832×832，实际 PNG 为 1254×1254。因此新界面必须分别展示请求尺寸与实际尺寸，不能仅回显请求参数。
- 普通 Codex 模型目录是对话模型能力来源；没有证据证明它会列出图片端点可用型号，不能直接拿它做生图模型下拉框。

## 第一阶段：做可验证的模型接入

新增一个独立的图片模型能力表，例如 `src/image-models.js`。记录候选型号、显示名称、允许质量档位、支持的操作、验证状态和验证时间。不要与普通模型的上下文窗口、Fast 或推理等级混在一起。

建议初始记录如下：

| 标识 | 当前订阅验证状态 | 行为 |
| --- | --- | --- |
| `gpt-image-2` | 本项目已完成生图和单图编辑实测 | 保持现有默认 |
| `gpt-image-2.5-flare` | 待订阅端验证 | 先作为受控测试目标；通过后开放选择 |
| `gpt-image-2.5-sunburst` | 待订阅端验证 | 单独验证生成、编辑及质量档位后开放 |

这三个名称中的后两个已被公共 API 文档确认，但订阅端是否接受仍未知。验证结果也不能从一个账号推广为所有账号可用。

工具增加可选 `model` 参数；缺省使用用户保存的生图模型，未设置则使用现有 Image 2。建议优先级为：本次明确选择 > 用户生图设置 > 兼容默认。模型和质量必须联合校验；请求旧模型的 `max` 应在发送前明确拒绝，不悄悄改成 `high`。

`src/index.js` 注册默认生图模型和质量设置，并传给图片工具。`src/capability-settings.js` 负责纯参数校验；`src/capability-preferences.jsx` 增加折叠的“图片生成”设置。账户切换要重新判断可用性，不能沿用上一账号的“已支持”结论。

生成和编辑共用模型解析与请求构造。保留原有参考图权限检查、会话归属、原图完整性验证和图片尺寸边界。旧图片仍可作为新模型编辑的参考；不要因为创建模型不同就丢弃引用。

## 第二阶段：让用户知道实际用了什么

界面采用明确型号和用途标签，如“Flare · 日常”“Sunburst · 精细编辑”，另设质量选项。精细编辑不等于自动使用最高质量；验证初期保持 `low` 小图测试，普通使用不自动升级到 `max`。

结果新增可选信息：请求模型、服务端报告模型、请求质量、服务端报告质量、实际宽高。只有响应明确提供、且语义经核对的模型信息才显示为服务端报告值；缺失时显示“服务端未报告”，不能把请求值复制过去作为验证证据。新增结果字段保持可选，历史消息仍能正常显示。

若服务端不支持该型号，明确说明并让用户自行选择现有模型重试。不自动改投付费 API、不在超时后暗中重复生图，也不把错误吞掉后用旧模型输出标成新模型。未经确认的失败不能一律归为型号不支持，例如授权过期、限额和网络错误应分别处理。

## 第三阶段：按接口证据增加高级功能

- **更精细的区域编辑**：现有编号标注继续可用。只有订阅编辑接口明确接受蒙版时才实现真正的 mask；不能把文字标注说成像素区域约束。
- **生成过程预览**：需确认订阅端的流式协议、取消语义和最终帧识别，再做渐进预览。现有下载进度不是生图进度，不伪造百分比。
- **更多输出格式**：涉及解码、媒体类型、文件名、原图存储、哈希校验和下载的整条链路，应独立修改和验证。第一阶段继续 PNG 足以完成新模型接入。

这些项目不应阻塞基础模型支持，也不应在缺乏订阅接口契约时提前露出可操作开关。

## 验收与合入条件

先通过官方客户端/订阅接口证据确认可接受的模型标识，再分别进行低质量小图生成和明确参考图编辑。采用一次调用一个条件的方式，保存脱敏的请求字段、响应元数据、PNG 尺寸、耗时和下载校验结果；不保存凭据，不为模型身份猜测反复生成。

本地测试至少覆盖：旧模型缺省行为不变；两个新模型的参数选择；质量组合拒绝；未知型号拒绝；账号切换；HTTP 鉴权/限额错误；编辑参考图不丢失；服务端型号未报告；实际尺寸不同；原图下载与旧消息兼容。随后用官方稳定版和 alpha 的实际依赖、安装包和浏览器完成回归。

建议纳入 1.15.0 的范围是模型选择、质量档位、结果信息和已验证的新模型生成/编辑。Flare 可以作为验证通过后的推荐选择，但是否更改升级用户的默认值应单独决定；现有已保存选择不覆盖。Sunburst、高质量档位和高级协议分别验证，不能由一次 Flare 成功代替。完成研究不等于完成实现，完成本地测试也不等于订阅实测通过；仍遵守先验收、不发布的要求。

当前 [内置生图文档](https://learn.chatgpt.com/docs/image-generation)仍写 `gpt-image-2`。它可能更新滞后，也可能对应保留的接口名称；本文不据此断言 2.5 不可用或旧名称已自动指向 2.5。

## 补充研究：订阅选择的证据边界

公开 API 支持选型号、订阅请求体包含 model、订阅服务真正按型号执行，是三件不同的事。当前只确认前两项，尚未完成第三项的 2.5 实测。也没有找到官方订阅接口的图片型号枚举或选择契约。不要用界面有下拉框、HTTP 200 或请求参数回显替代后端型号证据。

验证应分层记录：请求被拒绝；请求成功但型号未报告；服务端明确报告目标型号。再按账号、型号、生成/编辑操作和质量档位记录结果。即使成功响应报告型号，也不外推其他账号权限。若服务端忽略 model 或只接受旧别名，则保留“订阅默认”路线，不提供虚假的型号选择。当前阶段不能承诺 1.15.0 一定开放两款 2.5。

Luna 只是低成本验收时选择的对话模型。检查 src/index.js 的工具注册和 src/codex-images.js 的执行逻辑，未发现 Luna 专属限制。其他能调用该工具的对话模型可以使用相同生图链路；仍受 DSH 的工具可见性、账号授权及模型工具能力影响。已实测 Luna 不代表已对所有对话型号逐一实测。验收应以不消耗生图额度的工具注册/调用契约检查覆盖型号切换，真实出图只选代表性路径。

## 官方图片工作流与插件产品化

[官方图片文档](https://learn.chatgpt.com/docs/image-generation)描述 Focused 单图查看、Canvas 同会话图片查看、多选图片并提交评论继续编辑。这些是可借鉴的交互行为，不依赖订阅端开放 2.5。以下为本项目设计，尚未实现。

| 功能 | 当前代码 | 建议实现 |
| --- | --- | --- |
| 单图查看 | 已有缩放、平移、键盘操作和原图下载 | 复用现有查看器，补实际尺寸和模型信息 |
| 同会话画廊 | 查看器支持 items，但 client-images.jsx 每次只传一个条目 | 从当前会话图片结果派生目录，按附件引用去重，点击定位；缩略图懒加载，不预取所有原图 |
| 多选继续编辑 | 工具接受 1–5 个参考图，界面主要为单图入口 | 显式选择、排序、注明内容图/风格图用途，提交前展示引用清单；只传所选图片 |
| 图上评论 | 已有编号点、备注、干净原图和标注参考图 | 保留编号对应，支持多图评论；标注图也计入当前 5 张上限，不截断或静默丢图 |
| 修改前后对比 | 未发现独立对比入口 | 在明确父图关系下提供并排或滑杆；不同尺寸不声称像素对齐，不推断多参考图的唯一父图 |
| 编辑历史 | 当前通过会话消息保留结果 | 保存可选 parent/reference 引用及本次修改说明；分支保留，恢复旧图仅选择旧引用，不覆盖原文件 |
| 编辑草稿 | 当前异步创建附件后设置输入内容 | 原子提交或版本检查：准备过程中用户已输入则不覆盖，失败释放临时附件，重复点击不重复附加 |

多选代表一个编辑请求的多个参考，不代表对每张图各调用一次。若将来增加批量独立编辑，须独立显示任务数并允许逐项取消，不能借多选暗中增加调用。所有本地查看、评论和对比操作不触发生图。

## 可独立开关的功能设计

使用集中 imageFeatures 配置和统一有效状态计算，避免每个组件维护不同默认值。下表是建议默认值；现有用户迁移保留已有生成和编辑体验。

| 设置 | 建议默认 | 关闭语义 |
| --- | --- | --- |
| 图片生成 | 开 | 禁止无参考图的新生成；历史图片仍可查看 |
| 图片编辑 | 开 | 隐藏继续编辑入口，服务端拒绝有参考图的编辑请求 |
| 增强查看器 | 开 | 使用已验证的 DSH 原生查看器回退；缺少原生能力时保留可访问的基础查看和下载 |
| 同会话画廊/多选 | 开，完成功能验收后 | 保留单图查看和单图编辑 |
| 图上标注 | 开 | 不创建或发送标注参考；保留已有备注，不删除用户数据 |
| 修改前后对比 | 开，完成功能验收后 | 仅隐藏对比操作，原图和历史不变 |
| 结果详细信息 | 关 | 折叠型号、尺寸、质量等详情，用户仍可展开查看 |

生成和编辑独立控制，支持只编辑已有图片。增强查看器关闭时，画廊、标注、对比等依赖项显示不可用及原因，但保存原选择，重新开启时恢复。用户开关只能收窄实际能力，不能让未验证的模型、蒙版或流式协议变为可用。

服务端在执行入口读取最新功能设置，不能只隐藏按钮；工具展示能力也需与设置一致。关闭功能不删除已生成内容，不自动中止已提交的请求，不自动再发请求。严格布尔校验、旧配置默认、设置变化、请求排队后关闭、账号切换和历史消息回放均需覆盖。

实现落点：capability-settings.js 统一解析与校验；index.js 的偏好存储/RPC 和图片工具接入有效配置；client.jsx 向图片卡片和查看器注入响应式配置；client-images.jsx 组装操作和当前会话图片目录；subscription-image-viewer.js/.jsx 处理查看、选择与评论。扩展现有模块，不另建一套重复图片存储或整套宿主产品框架。

交付拆为三个可审查部分：先完成独立开关与旧行为回归，再做画廊/多选/草稿和对比，最后按订阅证据启用新图片型号。模型接入结果不阻塞纯本地产品体验改进。每部分在官方 DSH 安装候选包验收；本文件仍只是研究设计，本轮没有发布或执行 2.5 生图请求。

## 官方发布公告复核与 Sketch 缺口

进一步读取 [9 月 8 日发布公告](https://openai.com/index/introducing-chatgpt-images-2-5/)后确认：Images 2.5 正向 ChatGPT、Work 和 Codex 各档用户推出；公告同时将 Flare/Sunburst 作为 API 型号介绍。因此“订阅产品是否升级”已有肯定的官方证据，不能继续只引用旧内置生图文档。尚未确认的是我们使用的订阅端点怎样映射新能力，以及是否允许手动选择两个 API 型号。

公告明确介绍 @Sketch、创作模板、图片评论及提示词分享。[帮助中心](https://help.openai.com/en/articles/11084440-im)给出移动端 Sketch 操作：@ 选择 Sketch、选色绘画、擦除/撤销、确认后附加文字发送。帮助页说明模板尚未在 Work 提供；不能据发布公告推断每项界面功能在所有客户端同时可用。

代码搜索 src 无 Sketch 实现。目前 image-edit-reference.js 绘制的是编号标注参考图；subscription-image-viewer.jsx 是点标注而非自由笔画。这是实际缺少的产品能力，不是用户没有找到入口。

### 草图接入的具体路径

1. 在输入框提供“草图”操作，打开本地 Canvas 画板；支持空白画布、画笔、颜色、粗细、橡皮、撤销/重做和清空。笔画保存逻辑坐标，缩放与高 DPI 显示不改变导出构图；限制画布像素、笔画数量和历史内存。
2. 草图只在用户确认时导出 PNG。复用 client.jsx 已使用的 conversation.createDraftImages、conversation.input.for(actx).addImages 和 releaseDraftImages；失败释放临时附件，取消不发送任何生图请求。保存草图不覆盖已有输入文字。
3. 空白草图创作通过参考图链路发送给现有 codex_image_generate，明确提示“按草图构图生成成品”，而非发送 @Sketch 字符串到订阅端等待服务端弹出画板。已有图片上涂画则保留干净原图和另一个绘图参考，并说明哪些笔迹仅为指导。草图不等于 API mask，不保证修改严格限于笔迹区域。
4. 可增加 sketchEnabled 独立开关。关闭保留既有草图附件和用户数据，只停止新增画板操作；生成/编辑的执行权限仍依照参考图请求规则。草图生成目前走有参考图的编辑端点，产品说明必须处理“只开生成、关编辑”的依赖，不能绕过编辑开关。
5. 本地安装的 DSH 会话包 0.1.2-rc.1 类型已发现 conversation.input.left/right/overlay 扩展槽，按钮/弹层有现成接入位置。contract/input.d.ts 还明确包含支持 @ 的 InputTriggerController，以及 slash/input-consume-token 作用域事件，后者带 token/span 校验，可在启动画板时只消费触发词，保留其他输入。自动补全的 source 注册接口仍需在对应提供者核对，不能仅凭 controller 类型假定已经完成注册；无需拦截全局键盘或替换宿主编辑器。首版同时提供明确按钮入口。

草图功能不需要先证实 Flare/Sunburst 型号选择，也不需要新增付费 API 路线。应先以本地笔画、PNG 导出、附件引用和取消/草稿保留测试验证，再用 Luna 做一次低质量参考草图生成实机验收。

创作模板可用项目自有的海报、商品图、图标等结构化表单生成可编辑提示词，设独立 templatesEnabled；提示词复用可先做复制/本地导出，不上传或自动创建公开分享链接。选区编辑、改比例和文字位置指导需分别标注“参考引导”与已验证的真实接口参数，避免把宿主界面能力误当成订阅协议字段。

额外检查了本机 Codex 可执行文件的相关可读字符串：发现的 gpt-image-2 内容主要是内嵌 CLI/API 技能说明，未找到 gpt-image-2.5 或订阅图片端点字符串。此检查不是订阅后端证据，也不能据此判断新型号不可用；后续验证应以实际请求/响应或明确客户端契约为准。
